# PMOAgent 기능 구현·검증

## 1. 작업 기준 확인

- 작업 대상이 PMOAgent 저장소인지 확인한다.
- 저장소 루트의 AGENTS.md와 변경 대상 경로에 적용되는 추가 지침을 읽는다. 이 스킬로 프로젝트 업무 규칙을 새로 정의하거나 덮어쓰지 않는다.
- 기존 코드, README, 의존성 파일, DB 스키마, 테스트 및 작업 중인 변경을 확인한다.
- 요청한 기능에 필요한 파일만 읽고 기존 구조와 업무 함수를 우선 재사용한다.
- 저장소가 초기 상태라면 AGENTS.md의 기술 환경과 개발 순서에 맞춰 최소 실행 구조를 만든다. LLM 연동을 기본 화면 구현의 선행 조건으로 삼지 않는다.

## 2. 요구사항과 완료 기준 정리

- 이번 요청의 입력, 출력, 저장 대상, 오류 처리, 사용자 확인 단계와 완료 기준을 짧게 정리한다.
- 확정된 업무 규칙, 구현상의 선택, 업무상 미확정 사항을 구분한다.
- ID의 의미, 중복 필드의 원본 위치, 매출·매입단가 적용 방식 등 데이터 의미가 모호하면 기존 문서와 코드를 먼저 확인한다.
- 중요한 미확정 업무 규칙은 사용자에게 질문하고 해당 규칙에 의존하지 않는 개발은 계속한다. 폴더명 등 일반적인 구현 선택에는 합리적인 기본값을 사용한다.
- AGENTS.md의 MM 설명만으로 월별 분모, 휴일 달력, 시작·종료일 포함, 반올림 방식까지 확정했다고 간주하지 않는다. 계산 공식과 구매시스템의 확인 사례가 부족하면 계산 결과를 미설정으로 처리한다.
- 요청하지 않은 기능과 미확정 프레임워크를 선제적으로 도입하지 않는다.

## 3. 데이터와 업무 함수 구현

- 변경에 필요한 데이터 구조와 관계를 설계하고 설계 내용을 프로젝트 문서에 기록한다.
- 기존 데이터가 있으면 스키마 변경 전 백업·마이그레이션·복구 방법을 마련한다. 기존 DB를 삭제하거나 초기화해서 변경을 해결하지 않는다.
- DB 접근, 업무 로직, 화면, LLM 연동을 분리한다. 폼과 자연어 도구가 같은 업무 함수를 호출하도록 구성한다.
- 필수값·날짜·금액 검증과 실패 시 저장 차단을 업무 함수에서 처리한다.
- 관련 데이터와 변경 이력 저장을 하나의 트랜잭션으로 처리한다.
- 재실행·재시도에 따른 중복 등록과 체크리스트·알림 중복을 업무 함수 및 DB 제약으로 방지한다.
- 계산 기능에는 입력값, 적용 기간, 단가 단위, 적용 규칙 및 계산 근거를 확인할 수 있는 구조를 마련한다.
- 확정 검수의 입력값과 규칙을 보존한다. 단가 등 원본 정보 수정으로 과거 확정 결과를 자동 덮어쓰지 않는다.

## 4. 화면과 도구 연결

- Streamlit 화면에서 입력 → 미리보기 → 사용자 확인 → 저장 결과 확인의 흐름을 구현한다.
- 조회는 확인 없이 수행할 수 있도록 하고, 등록·변경은 AGENTS.md의 확인 기준을 따른다.
- 사용자 확인 후 저장에 실패하면 성공으로 표시하지 않는다. 입력값을 보존하고 오류와 재시도 방법을 안내한다.
- 미설정, 해당 없음, 실제 0값, 실패를 구분하여 표시한다.
- 실제 신청·예약·구매시스템 승인 여부와 앱 내부 초안·확정 상태를 구분한다.
- LLM 기능을 요청받은 경우 입력·출력이 정의된 도구를 연결하고 기존 업무 함수를 호출한다. LLM이 생성한 임의 SQL을 실행하지 않는다.
- API 미설정·오류 상태에서도 수동 화면과 기본 업무 기능이 동작하게 한다.
- 회사의 데이터 전송 기준이 미확정이면 가상 데이터로 LLM 연동을 검증한다.

## 5. 변경에 맞는 검증 수행

- 핵심 업무 로직의 정상·실패·경계 사례를 자동 테스트로 검증한다. 화면 문구 등 단순 변경에 불필요한 테스트를 추가하지 않는다.
- 테스트에는 가상 데이터와 별도 임시 DB를 사용한다. 실제 업무 DB를 변경하지 않는다.
- 이번 변경과 관련된 AGENTS.md의 검증 기준을 선택하여 실행한다.
- 인력·투입 변경에서는 동명이인 ID 구분, 날짜 오류, 저장 취소·재실행, 변경 이력과 저장 실패 시 롤백을 확인한다.
- 체크리스트에서는 생성 누락·중복과 해당 없음 사유를 확인한다.
- 계약 알림에서는 종료 14일 전·당일·만료 후, 종료일 변경과 반복 실행을 확인한다.
- 계산에서는 확인된 구매시스템 사례, 월 경계, 일부 기간 투입, 과제 배분과 합계 일치를 확인한다. 기준 사례가 없으면 계산 일치를 검증했다고 보고하지 않는다.
- 관련 화면은 실제 사용자 흐름으로 확인한다. 실행 환경이 없어 확인하지 못한 부분은 구체적으로 기록한다.
- 관련 테스트가 통과하면 추가 변경이나 미해결 위험이 없는 한 같은 검증을 반복하지 않는다.

## 6. 문서 정리와 완료 보고

- 실행 명령, 의존성, 설정, DB 위치, 초기 실행 및 테스트 방법을 프로젝트 README에 실제 구현 기준으로 기록한다.
- 미확정 업무 사항은 기존 TODO를 재사용하고, 해결 근거 없이 완료 처리하지 않는다.
- 커밋 전 diff를 확인하여 실제 인력·계약 데이터, DB, 비밀값과 관련 없는 변경이 포함되지 않게 한다.
- 사용자의 커밋·푸시 요청과 적용되는 저장소 지침에 따라 변경을 반영한다. 승인 없이 관련 없는 변경을 포함하거나 이력을 강제로 덮어쓰지 않는다.
- 한국어로 구현한 동작, 변경 파일, 실행 방법, 실행한 검증과 결과, 미실행 검증 및 남은 TODO를 보고한다.
- 테스트 통과와 사용자 업무 검증 완료를 구분한다. 미완료 기능을 완료했다고 보고하지 않는다.
